# Передача сессии — 2026-09-14

Для Claude Code (или человека), который продолжает работу на Windows-ПК
пользователя. Сессия шла на Mac; здесь всё, что нужно знать, чтобы
продолжить без того диалога. Общение с пользователем — на русском.

## Где мы

Проект — Dota 2 Draft Helper: локальное приложение (Python stdlib +
HTML/JS), подбор героев против вражеского драфта. Репозиторий
`Dtkek/dota2-draft-helper` (приватный), ветка `main`. Архитектура и
история — в `app/README.md` и `_project_dota2_draft_helper.md` (§4–5).

Сделано за 2026-09-14 (всё в `main`, всё собрано в релиз `latest`):

1. Сборка exe для Windows через GitHub Actions (`.github/workflows/build-windows.yml`),
   релиз `latest` обновляется на каждый push в `main`.
2. STRATZ как второй источник матчапов (`app/sources/stratz.py`): ранги парами,
   синергия союзников, позиции по данным. Снимок `app/data/stratz_fallback.json.gz`
   обновляет workflow `update-stratz.yml` по пятницам (секрет `STRATZ_TOKEN`
   в репозитории уже добавлен, прогон вручную прошёл успешно).
3. Собственное окно приложения (`app/window.py`, pywebview) с переключателем
   «поверх окон». На macOS проверено. На Windows — **не работает у пользователя**,
   см. ниже.

## Решено: окно на Windows не открывалось, открывался браузер

**Причина оказалась не в кириллице.** Разбор на самом ПК пользователя
(14.09.2026, вечер): версия `.7` отрабатывала обход как задумано — DLL
бралась из копии по чисто ASCII-пути `%LOCALAPPDATA%\dota2-draft-helper\
pythonnet` — и всё равно падала с той же ошибкой. Прямая загрузка сборки
через .NET дала настоящий текст:

```
Could not load file or assembly '...\Python.Runtime.dll' or one of its
dependencies. Operation is not supported. (Exception from HRESULT: 0x80131515)
```

`0x80131515` — .NET Framework отказывается грузить сборку с меткой
«скачано из интернета» (поток `Zone.Identifier`). Windows метит скачанный
ZIP, проводник переносит метку на каждый распакованный файл: на машине
пользователя помечены были 311 файлов из 314, включая все 160 DLL.
После `Unblock-File` по папке окно открылось сразу.

Почему обход `.7` не помогал: `shutil.copytree` в Python 3.8+ копирует
файл через `CopyFile2`, а она переносит и альтернативные потоки — метка
аккуратно переезжала в ASCII-папку вместе с DLL.

Почему этого не ловил CI: на раннере сборка своя, локальная, метки на
ней нет. Проверка запускала exe из папки с кириллицей, но «чистый».

Что сделано (коммит ниже):

- `app/window.py`: `_ascii_runtime_workaround` → `_dotnet_runtime_workaround`.
  Снимает метку со всей `_internal` (через .NET грузится не только
  pythonnet, но и WebView2), и с копии runtime тоже. ASCII-обход
  оставлен: он ничего не стоит, если путь и так ASCII.
- `.github/workflows/build-windows.yml`: проверка запуска теперь сама
  метит файлы `Zone.Identifier`, то есть воспроизводит ситуацию
  пользователя, а не «чистую» сборку.
- `app/server.py`: при `Failed to resolve` / `0x80131515` подсказка про
  «Разблокировать», а не про кириллицу.
- `app/tools/diagnose.py`: раздел 6 — pywebview, .NET Framework,
  WebView2, метки на файлах, кириллица в пути.

Ниже — исходная хронология, оставлена как есть: по ней видно, как один
и тот же симптом трижды объяснили не той причиной.

### Как это выглядело раньше

Машина пользователя: Windows 11 (10.0.26200), exe лежит в
`C:\Users\Richa\OneDrive\Рабочий стол\dota2-draft-helper\`.

Хронология:

- Версия `.4`: exe падал сразу. Лог с машины пользователя:
  `RuntimeError: Failed to resolve Python.Runtime.Loader.Initialize from
  ...\Рабочий стол\dota2-draft-helper\_internal\pythonnet\runtime\Python.Runtime.dll`
  из `clr_loader\netfx.py`. Диагноз: кириллица в пути. `clr_loader`
  кодирует путь к DLL в UTF-8 и отдаёт в C++-загрузчик `ClrLoader.dll` как
  `char*`, тот читает его как ANSI — путь превращается в мусор.
- Версия `.5`: падение больше не молчаливое (traceback + ожидание Enter),
  при ошибке окна — откат в браузер.
- Версия `.6`: перезапуск exe по короткому имени 8.3. **Не помогло** —
  у пользователя открылся браузер. Вывод консоли с `.6` пользователь не
  прислал, причина неизвестна (возможно, 8.3-имена выключены на диске или
  OneDrive-папка их не даёт).
- Версия `.7` (текущая, коммит `7d7fa45`): перезапуск убран; вместо него
  `window._ascii_runtime_workaround()` копирует `pythonnet/runtime` в первую
  папку с ASCII-путём (`%TEMP%`, `%LOCALAPPDATA%`, `%ProgramData%`, `C:\Temp`)
  и подменяет `pythonnet.__file__` — `pythonnet.load()` строит путь к DLL
  от него. **На раннере GitHub это проверено ровно в такой же ситуации**:
  проверка в workflow копирует exe в `…\Рабочий стол\dota2-draft-helper`,
  запускает, в логе есть строка «кириллица в пути: pythonnet берёт DLL из
  копии …», окно открылось. У пользователя — **всё равно браузер**.
  Вывод консоли снова не получен.

## Если окно снова не откроется

Получить вывод консоли — без него всё остальное гадание (именно из-за его
отсутствия причину и не находили три версии подряд):

```
cd /d "C:\Users\Richa\OneDrive\Рабочий стол\dota2-draft-helper"
dota2-draft-helper.exe
```

Смотреть:

1. Строку `Драфт-хелпер, версия …` — сверить с описанием релиза `latest`.
   Если старее — скачан не тот архив; прямая ссылка
   https://github.com/Dtkek/dota2-draft-helper/releases/download/latest/dota2-draft-helper-windows.zip
2. Есть ли строка «снята метка «скачано из интернета» с N файлов».
3. Строку «окно не открылось: <тип>: <текст>» — это и есть причина.

Или `diagnose.bat` — раздел 6 проверяет pywebview, .NET Framework,
WebView2, метки на файлах и кириллицу в пути (нужен Python на машине).

Оставшиеся гипотезы, если метка снята, а окно всё равно не открылось:

- **Папка только для чтения** — метку снять не удалось; в логе будет
  видно, что снято 0 файлов, а диагностика покажет, сколько помечено.
  Перенести папку в место, доступное на запись.
- **WebView2 Runtime не установлен** — pywebview не должен падать
  (откатывается на MSHTML), но проверить: `reg query
  "HKLM\SOFTWARE\WOW6432Node\Microsoft\EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}"`.
  Установка: https://developer.microsoft.com/microsoft-edge/webview2/ (Evergreen Bootstrapper).
- **Антивирус** блокирует `Python.Runtime.dll` или `WebView2Loader.dll`
  из `_internal` — смотреть журнал Защитника.
- **OneDrive «файлы по запросу»**: часть файлов `_internal` — заглушки без
  содержимого до первого открытия. На машине пользователя это проверено,
  файлы были на месте, но у OneDrive-папки это стоит исключать первым.
- **`%TEMP%` недоступен для записи** — тогда копия DLL не создаётся;
  в логе будет «нет папки с ASCII-путём для копии DLL».

Быстрый обходной путь, если нужно просто работать: снять блокировку
(`Get-ChildItem -Recurse | Unblock-File` в папке приложения). В браузере
приложение работает полностью; окно — удобство, не функция.

## Как проверять изменения

- Локально из исходников: `python app\server.py` (нужен `pip install -r
  app\requirements-window.txt` для окна). Ключи: `--browser`, `--on-top`,
  `--no-browser`, `--port`.
- Каждый push в `main` собирает exe (~8 мин) и обновляет релиз `latest`.
  Дата у релиза остаётся старой (обновляется один и тот же релиз);
  версию смотреть в описании релиза (хеш коммита) или в первой строке
  консоли exe.
- Проверка в workflow запускает exe из папки с кириллицей и падает, если
  сработал откат в браузер. Лог шага «Проверка запуска» печатает весь
  вывод exe.
- В workflows файлы можно пушить только токеном с правом `workflow`
  (в Keychain на Mac его не было; на ПК настроить `gh auth login`).

## Чего в этом файле нет намеренно

Токены: GitHub PAT и STRATZ. Они были в диалоге на Mac открытым текстом
и в репозиторий не кладутся. GitHub PAT — https://github.com/settings/tokens
(нужны `repo` + `workflow`); STRATZ — https://stratz.com/api (один токен на
аккаунт, он уже лежит в секретах репозитория как `STRATZ_TOKEN`).
